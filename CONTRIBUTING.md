# Contributing

Thank you for your interest in contributing to this repository.

This project is a professional portfolio codebase. Contributions are welcome when they improve code quality, accessibility, performance, maintainability, documentation clarity, security posture, or deployment reliability.

## Contribution Principles

Please ensure all contributions are:
- Professional in tone and scope
- Relevant to the repository’s goals
- Small and reviewable when possible
- Secure by default
- Consistent with the project’s architecture and visual direction
- Free from secrets, credentials, and sensitive information

## Ways to Contribute

You can contribute by:
- Fixing bugs
- Improving documentation
- Refining UI responsiveness or accessibility
- Strengthening performance
- Improving SEO or metadata handling
- Modernizing developer tooling
- Hardening configuration and deployment safety
- Proposing reusable architecture improvements

## Before You Start

Before opening a pull request:
1. Review the existing documentation.
2. Confirm the change fits the repository scope.
3. Check whether the change affects security, deployment, or public presentation.
4. Keep commits focused and easy to review.

## Development Workflow

1. Fork the repository.
2. Create a focused branch.
3. Make your changes.
4. Test locally.
5. Verify that no secrets or unnecessary generated artifacts are included.
6. Open a pull request with a clear summary.

Example branch names:
- `docs/improve-readme`
- `fix/mobile-layout-overflow`
- `chore/update-dependencies`
- `feat/add-accessibility-improvements`

## Pull Request Expectations

A good pull request should include:
- A concise title
- A summary of what changed
- Why the change matters
- Screenshots for UI changes, where relevant
- Testing notes
- Any deployment or configuration impact

## Coding Expectations

Please follow these standards:
- Prefer readable, maintainable code over clever shortcuts
- Keep naming clear and consistent
- Preserve responsive behavior
- Avoid unnecessary dependencies
- Favor accessible and semantic UI patterns
- Document non-obvious behavior
- Keep configuration explicit and safe

## Security Requirements

Do not submit:
- API keys
- Tokens
- Passwords
- Private certificates
- Production secrets
- Unreviewed third-party code of uncertain origin

If your contribution relates to a vulnerability, do not open a public issue. Follow the process in [SECURITY.md](./SECURITY.md).

## Documentation Contributions

Documentation improvements are encouraged, especially for:
- Setup instructions
- Deployment steps
- Troubleshooting
- Accessibility guidance
- Architecture notes
- Governance clarity

## Review Process

All contributions are reviewed at maintainer discretion. The maintainer may request revisions for:
- Scope control
- Security concerns
- Style consistency
- Documentation completeness
- Deployment safety
- Professional presentation quality
